# Восстановление после сбоя

## Незавершённая операция

1. Приостановите управление и сохраните журналы и БД. Сопоставьте события по operation_id.
2. Найдите операцию в `bid_change_operations`, исходное решение в `bid_decisions` и причину блокировки в `runtime_states`. После старта PENDING/SENT переходит в UNKNOWN с FAIL_SAFE. Симулятор сверяет существующую квитанцию и состояние чтением.
3. При неопределённом состоянии сохраняйте блокировку до выяснения результата. Для будущего реального адаптера сверяйте модель, ставку и действие владельца через read-only API и кабинет. Любой новый запрос на изменение требует нового решения и подтверждения.

## Повреждение БД или неудачная миграция

1. Остановите сервис через `docker compose stop`. Сохраните повреждённый файл и, если существуют, его файлы `-wal` и `-shm` в отдельном каталоге. Оставьте оригиналы доступными для анализа.
2. Выберите проверенную копию, обычно ближайшую ежедневную или `before-migration-*.db` для отката схемы. Под тем же пользователем и в том же окружении задайте DATABASE_URL на файл копии. Выполните `python -m app.main backup --file /path/to/restored.db`, где restored.db — новый файл.
3. Сверьте версию Alembic, объявления, историю решений, бюджеты и операции UNKNOWN/PENDING/SENT на восстановленном файле. Backup выполняет SQLite integrity check и foreign key check. Проверьте дату снимка, изменения после неё могут потребовать восстановления из журналов.
4. В остановленном сервисе назначьте восстановленный файл рабочим либо переместите его в путь manager.db после удаления оригинала и его sidecar-файлов из рабочего каталога. Проверьте права доступа пользователя сервиса. Для отката схемы запускайте совместимую версию приложения. Для повторной миграции разберите причину первой ошибки и испытайте обновление на отдельной копии.
5. Запустите DRY_RUN и проверьте `health` и `readiness`. Сверьте неопределённые операции и бюджет с кабинетом до любых действий вне локального контура.

Для ручного снимка остановленной базы используйте `python -m app.main backup --file /path/to/copy.db` с DATABASE_URL исходного файла. При работающем сервисе внутреннее задание копирования читает WAL через SQLite backup API. Простое копирование основного manager.db при работе может потерять подтверждённые транзакции.
