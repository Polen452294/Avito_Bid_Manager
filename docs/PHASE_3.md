# Фаза 3. Мониторинг поисковых позиций

Мониторинг ведёт историю для 1–5 настроенных объявлений. Каждое наблюдение привязано к ID, запросу, региону и фильтрам. История хранится в SQLite, время приводится к UTC. Одинаковое наблюдение из одного источника повторно не записывается.

| Источник | Состояние |
| --- | --- |
| Manual | Импорт JSON и CSV. Подлинность переданных наблюдений проверяет оператор. |
| Mock | Последовательность наблюдений для разработки, тестирования и воспроизведения. Адаптер поддерживает задержки и исключения. |
| Official | Возвращает UNSUPPORTED. Подтверждённого метода чтения оперативной позиции нет в проверенных контрактах проекта. |
| External | Принимает асинхронный адаптер. Проверен с тестовыми ответами. Боевой поставщик не подключён. |
| Browser | Отключён. Разрешение на автоматизированную проверку выдачи не подтверждено. Playwright не запускается. |

Официальные страницы [каталога API](https://developers.avito.ru/api-catalog), [инструмента «Среднее место в поиске»](https://www.avito.ru/company/press/mestovpoiske) и [правил](https://www.avito.ru/legal/rules/terms-of-use) в ходе проверки не открылись. Доступность инструмента в конкретном аккаунте, периодичность обновления и возможность API-выгрузки остаются непроверенными. Позиция, усреднённая за сутки или другой период, записывается с типом AVERAGE и исключается из оперативного анализа и расчёта ставки. При наличии границ периода заполняйте period_start и period_end.

[Avigram](https://avigram.io/api-documentation) документирует уведомления о новых объявлениях. Такой контракт не подтверждает получение места заданного объявления. [AIX](https://aixservice.ru/agreement) описывает мониторинг позиций, но публичный контракт чтения результатов и допустимость источника данных не подтверждены. Реальную оперативную позицию из разрешённого источника получить не удалось.

## Настройка

Сделайте резервную копию рабочей базы и примените миграцию 0002 командой `python -m alembic upgrade head`. Старые снимки сохраняются. Миграция рассчитана на движение вперёд.

1. Добавьте объявление через `python -m app.main add-item --file item.json` или Telegram. В queries задайте text, region, при необходимости filters как словарь строк и weight для приоритета.
2. Импортируйте наблюдения через `python -m app.main import-positions --file observations.json` или укажите CSV. Используйте заранее зарегистрированные ID. JSON содержит массив объектов. В CSV используйте имена полей как заголовки, а filters записывайте как JSON-объект внутри ячейки.
3. Запустите `python -m app.main serve`. Планировщик проверяет сроки опроса каждую минуту. Для контекста и источника применяется больший из интервалов объявления и источника. Попытка сохраняется до вызова адаптера. Официальный статус обновляется не чаще раза в сутки. Ручные записи появляются сразу после импорта.
4. Для тестового мониторинга передайте `serve --file mock.json`. Расставьте строки в порядке обхода объявлений и запросов и задайте provider как mock. Исчерпание сценария регистрируется как недоступность.

Пример строки JSON для зарегистрированного объявления:

```json
{"item_id":123,"search_query":"пример","region":"Москва","filters":{},"position":8,
 "position_type":"MIXED","checked_at":"2026-11-16T12:00:00Z","provider":"manual",
 "confidence":"0.9","status":"FOUND"}
```

У NOT_FOUND_IN_CHECKED_RANGE поле position пустое. checked_range может хранить глубину проверки. У UNVERIFIED может быть числовое место для истории, оно не участвует в оперативной оценке.

В личном чате администратора доступны /positions ID, /position_history ID и /queries ID с JSON-массивом запросов. Команда позиций показывает свежие результаты с источником и уверенностью. Для непроверенной выдачи отображается «Нет достоверных данных». При включённом боте переход к устойчивому ухудшению или недоступности источника вызывает уведомление. Состояние последнего уведомления хранится в SQLite.

## Анализ и ставки

PositionAnalyzer рассчитывает среднее и медиану по сопоставимой серии одного источника и типа выдачи. Три последних однонаправленных наблюдения с общим сдвигом от двух мест отмечаются как тренд. Отчёты упорядочены по весу запросов. Регионы и наборы фильтров анализируются отдельно.

BiddingService.evaluate_history подаёт накопленные наблюдения в существующий BiddingEngine в DRY_RUN. Для рекомендации нужны свежие последовательные результаты с уверенностью от 0.8, проверенные сведения о ставке и достоверные расходы. Отказ источника или конфликт свежих позиций блокирует рекомендацию и сохраняется в журнале. Движок учитывает отсечку после последнего изменения и период стабилизации. Реальные записи ставок не выполнялись. Планировщик собирает позиции, а вызов evaluate_history требует отдельно передать проверенный снимок расходов.

Перед эксплуатацией подтвердите официальный контракт или получите документацию поставщика и разрешение на способ сбора. Затем проверьте на своём аккаунте выдачу по конкретному запросу, региону и фильтрам, фактическую задержку источника и работу уведомлений в тестовом Telegram-чате.
