## Как принимается решение

- Движок использует подтверждённую ставку, настройки объявления, снимок расходов и наблюдения. Он не выполняет сетевые запросы. Фаза 4 использует Target Position Bidding и для сохранённых объявлений с прежним именем стратегии.
- Данные сопоставляются по объявлению, тексту запроса, региону и фильтрам. Для решения подходят точные позиции из источников в `position_sources` с уверенностью от 0,8. Неудачный замер прерывает серию подтверждений. Повторные отметки времени, пересекающиеся интервалы и смешение источников или типов позиции блокируют решение.
- По умолчанию нужны подтверждения по всем запросам. При меньшем `min_position_coverage` основной запрос всё равно обязателен. Покрытие считается по сумме весов запросов с подтверждениями. Средневзвешенная последняя позиция доступна в журнале. Несогласованные направления, свежая неподтверждённая серия и слишком большой разброс времени наблюдений приводят к HOLD. На объявление рассчитывается одна ставка.
- Устойчивые позиции хуже `target_max` позволяют повысить ставку. Для пробного снижения вся серия должна достигать `target_max - hysteresis_positions` или более высокой позиции. В пограничной зоне ставка сохраняется. При устойчивой позиции выше `target_min` журнал отмечает это отдельным кодом.
- Следующее решение использует наблюдения, полученные строго после момента применения плюс время стабилизации. Для интервальных наблюдений проверяется начало интервала. Cooldown, минимальный интервал повышений и суточный лимит считаются по подтверждённым операциям.
- После успешной пробы можно повторить снижение. При ухудшении движок предлагает восстановить прежнюю ставку в пределах разрешённого шага. После подтверждённой попытки восстановления прежняя ставка становится нижним порогом для последующих проб. Порог сохраняется при перезапуске и в этой фазе автоматически не сбрасывается.
- Кандидат должен одновременно удовлетворять денежному и процентному пределу шага, диапазону объявления и сетке или списку API. Для пробного снижения шаг дополнительно ограничен допустимым обратным движением. Когда разрешённого значения в пределах шага нет, решение остаётся HOLD.
- BudgetController проверяет целостность статистики, дату по часовому поясу аккаунта, свежесть и остаток до защитного порога по объявлению и аккаунту. При неизвестных расходах или израсходованном лимите ставка сохраняется. Денежные суммы хранятся в целых копейках. Из-за задержки отчётности порог с резервом снижает риск перерасхода, но не является гарантией точного денежного лимита.

## Настройки объявления

| Группа | Поля |
|---|---|
| Целевая позиция | `target_min`, `target_max`, `hysteresis_positions` |
| Ставки и шаги | `min_bid`, `max_bid`, `increase_step_kopecks`, `decrease_step_kopecks`, `increase_step_percent`, `decrease_step_percent`, `max_step_kopecks`, `max_step_percent` |
| Время и подтверждения | `cooldown_minutes`, `stabilization_minutes`, `increase_interval_minutes`, `increase_confirmations`, `decrease_confirmations`, `max_changes_per_day` |
| Запросы | `queries` до пяти запросов с полем `weight`, `primary_query_index` с нуля, `min_position_coverage`, `max_query_skew_minutes`, `position_sources` |
| Расходы и расписание | `daily_budget`, `active`, `auto_enabled`, `active_hours`, `monitoring_interval_minutes` |

При отсутствии локальных настроек шага, подтверждений и дневного числа изменений используются настройки приложения. По умолчанию для повышения нужны два наблюдения, для снижения три, допускается четыре изменения в сутки. Стабилизация наследует cooldown. Ограничения шага по умолчанию составляют 1000 копеек и 20% текущей ставки. Общий дневной лимит и резерв настраиваются на уровне приложения. Без настроенных запросов движок выдаёт HOLD.

## Журнал и исполнение

Миграция `0003` добавляет версию структуры в журнал решений и время подтверждённого применения в журнал операций. Старые записи сохраняются. Для прежних успешных симуляций без отметки применения используется время операции. Новые решения содержат действие, причину и код причины, использованные наблюдения, итоговое покрытие, оценку позиции, ограничения, статус разрешения и ожидаемый эффект изменения.

В `serve` APScheduler собирает наблюдения и регистрирует DRY_RUN для новых данных, включая ручные импорты. Курсор истории хранится в SQLite вместе с решением. Один цикл обрабатывает объявления последовательно. Планировщик ограничен одним активным экземпляром задания, а приложение использует файловую блокировку SQLite. При отсутствии подтверждённых снимков ставки и расходов решение остаётся HOLD. Заполнение этих снимков реальными данными в данном режиме ещё не подключено.

ExecutionService принимает подтверждённые владельцем операции ASSISTED только для локального `MockBidProvider`. Перед отправкой он сверяет сохранённое решение, конфигурацию, текущую ставку, срок действия рекомендации, бюджет и допустимые значения. Резервирование выполняется транзакцией SQLite. После неопределённого результата сервис читает состояние, а повторной отправки не делает. При запуске незавершённые операции переходят в UNKNOWN. Подтверждённое чтение симулятора может закрыть собственную операцию Фазы 4, иначе блокировка сохраняется. Для прежних операций действует сверка через исходный адаптер и журнал. AUTO отключён на уровне конфигурации и исполнения.

В Telegram `/strategy ID` показывает настройки, а `/strategy ID {JSON}` обновляет выбранные поля. Запросы и веса задаются через `/queries ID [JSON]`. Команды `/budget ID`, `/history ID` и `/recommend ID` показывают лимиты, последние причины и результат ручного расчёта в DRY_RUN. Поле `auto_enabled` разрешает расчёт стратегии по объявлению. Режим исполнения при этом остаётся DRY_RUN.

## Проверка на локальных данных

```powershell
python -m pytest -q
python -m pytest tests/test_phase4.py -q
python -m app.main demo
python -m app.main backtest --file examples/phase4_backtest.json --position-origin fixture --assume-applied
```

Пример backtest выдаёт пробное снижение с 2000 до 1900 копеек, затем рекомендацию восстановления до 2000. Кадры задаются полями `now`, `observations`, необязательными `spending` и `bid_info`. В обычном replay передавайте фактически наблюдавшиеся ставки и позиции, а отметки кадров располагайте по возрастанию. С флагом `--assume-applied` ставка следующего кадра моделируется из решения. Позиции всегда берутся из входных кадров. Поля `position_origin` и `bid_origin` указывают происхождение отдельно. Смоделированная последовательность не измеряет влияние ставки на реальные позиции или расходы.

Проверка миграций создаёт отдельную временную SQLite, применяет `0001 → 0002 → 0003` с историческими записями и запускает `alembic check`. Для обновления рабочей базы остановите сервис, сделайте резервную копию и выполните `python -m alembic upgrade head` перед следующим запуском.

Для реального управления нужны подтверждённая модель продвижения, доступ к аккаунту, актуальные снимки ставки и расходов, разрешённый оперативный источник позиций для настроенных запросов и проверенный путь записи со сверкой результата. Фаза 4 проверяет эти правила локально. Реальные платные операции в этой проверке не выполнялись.
